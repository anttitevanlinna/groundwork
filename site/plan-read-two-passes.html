The clever way to hold it: a plan is flat to either eye alone — the depth you're approving lives in the disparity between two reads, never inside one.

Before you approve an agent's plan for a multi-file change, read it the way two eyes build depth — with two reads that catch different things: your situated read for the soft item only you can feel, and a second agent's branch-walk for everything you'd never hold in working memory. Neither read alone is the approval. The depth is computed from the gap.

The plan didn't gain depth because you stared harder with one eye. It was read twice, two different ways, and the gap fused.

Close one eye and the agent's plan is a flat page: three files, seven steps, a verification list, and an approve button already lit. Open the second eye and nothing on the page changes — yet now there's depth, and the depth is the only thing you were ever approving. It doesn't live in either read. It lives in the gap between them.

Left eye · your read

Shallow but situated.

You don't hold the whole design tree in working memory. What you hold is the nose: the soft item, the assumption that's wrong for this repo, the file that shouldn't be touched at all. You've seen what happens when the auth helper gets edited for a feature that had nothing to do with auth; the agent has never shipped your code on a Friday afternoon. That's the read no breadth can fake — and it's worthless until you make it specific.

So don't nod. In plan mode, pick keep planning with feedback, find one step, and quote its number and one word from it — because a quote forces the agent to revise the actual step, not nod at a vague worry:

not “looks good, one concern” — but “step 3, ‘update the auth helper’ — that's the wrong file for this change.”

↻ THEN CHECK THE REGENERATED STEP ACTUALLY SHARPENED.
“GOOD POINT” IS NOT A FIX. IF IT RE-SOFTENED, PUSH AGAIN — SAME QUOTE.

Right eye · agent walk-down

Exhaustive but unsituated.

The walk-down is your nose's inverse. Ask a second agent to dredge up every branch the plan left unresolved — the nullable-id question, the cache-or-live question, the retry-path question — including the dozen you'd never have kept in working memory. What it lacks is the nose: it can't feel which default would quietly break your codebase.

So run it as a sequence, not a dump. A list returns every branch at once; a read resolves them one at a time. Ask it to walk the branches it didn't resolve, one question with a recommended answer at a time, and let it run until it is out of branches:

you don't get to call it done early — and the recommendations are defaults, not prescriptions.

↻ REJECT AT LEAST ONE RECOMMENDATION THAT'S WRONG FOR THIS REPO.
IF YOU REJECTED NONE, YOU RUBBER-STAMPED THE SECOND READ TOO.

Fuse the two · the Monday-move is one line

Next multi-file plan an agent hands you, don't approve it — read it with the left eye and the right eye, approve only after both land, and the branch your push-back caught gets saved as a rule so the next plan in this repo arrives pre-shaped and the reading gets cheaper.

The proof you used both eyes, not one twice: you can name one thing your eye caught that the agent's walk-down never would have. If you can't, you read with one eye and called it depth — the agent did both passes and your situated read added nothing.

Where it sits: this is the personal foundation of Context & Guardrails. The same branch a second read surfaces is what a team later hardens into a shared judge or CI check — so the company's plan-quality stops depending on whether each person happened to read twice.
