Author the skill that shapes future sessions

The principle: test → learn → encode — and encode is the phase everyone skips, because by then the bug is fixed and the satisfaction is spent.

You ran the same kind of task twice; the second run still tripped on something the first one warned you about. Turn that named gap into a skill the next run inherits — the lesson packaged as a move that fires unprompted, not a diff you patch and forget. This is a personal-layer move that composes upward: one engineer's two-run lesson becomes the input to the whole team's kit.

A lesson you remember is ephemeral. A skill that fires is durable — the gap caught, not re-explained.
The mechanism · why two runs, not one

One run is an anecdote. Two runs are the material.

A scaffold catches only what it was shaped to catch. The first time you run a task, any failure you hit is just a failure — it could be the model having a bad day, a one-off, noise. The second run is where the signal is: when the same edge trips again against the very scaffold you built to prevent it, you're no longer looking at bad luck. You're looking at a gap the pattern itself didn't anticipate — and that contrast, baseline run versus packaged re-run, is the only honest evidence you have for what to encode. One run gives you a failure mode. Two runs give you a gap, and a shape for what to do about it.

The reflex at this exact moment is the enemy. The bug is in front of you, the fix is small, and the satisfying thing to do is patch the diff and move on — leaving the lesson nowhere. It evaporates not because the gap was subtle, but because nobody built the move that carries it forward. The diagram below shows the discipline that stops the evaporation: read both transcripts separately, quote the specific moment that went wrong in each, and only then name the one gap that cost the most. Naming-from-quotes is what keeps it honest — a generic summary means you didn't actually re-read both runs.

Here is the move most people get wrong on the way out: they reach for "skill" because a skill feels like the answer. It isn't always. Route the gap to its home before you build anything. A gap has three plausible homes, and they are not interchangeable — a rule in memory that would have prevented the mistake upstream; a sharper verifier that would have fired mid-run; or a new skill that packages a move for future tasks. Naming the home first is the thing that stops the skill from becoming a junk drawer — the place every gap gets stuffed because nobody decided where it actually belonged.

The upgrade move · felt → routed → fires

From a sticky note you'll forget to a move that fires unprompted.

When you've decided a skill is the right home, the second discipline is matching the skill's shape to the gap's shape. A qualitative drift — tone, judgement, the kind of thing a binary check can't see — wants a judge. A deterministic miss — a check that should have caught a concrete violation — wants a sharpened verifier. A recurring drift that keeps re-surfacing in new forms wants a gap-finder. Picking the wrong shape is the most common authoring miss there is: a verifier can't see drift, and a judge is overkill for a binary check. Practitioner-convergent menu · not a fixed taxonomy

Sharpened-verifier / judge / gap-finder are three shapes that cover most gaps — read them that way, not as a complete or authoritative classification. Same caveat on the trio of forms: a verifier (deterministic), a judge (LLM-based), and a gate (placed in CI) are three forms of the same thing — an automated check that an agent-produced artefact meets the bar. None is strictly superior; the shape follows the gap.

Now the counterintuitive bit about how you author it: not in an editor. Don't open a markdown file and type the skill — hand Claude the diagnosis, let it draft, push back, let it ship. The skill is supposed to encode what your codebase taught you across two real runs, and that knowledge comes out through interrogation, not dictation. You are the one who knows which moment actually went wrong; the draft will round it off into a generic best-practice unless you keep pushing it back toward the specific convention your session revealed.

Authoring isn't only adding, either. The same diagnosis that earns a skill very often retires a stale rule — one that the two runs proved was wrong, or dead weight. So the artefact you ship is a pair: the new SKILL.md, and at least one rule cut from your local rules file, the deletion visible in git history. Compound by subtraction. What "Test" actually means · in practice

The test is whether it fires — not whether it reads well.

A skill passes its test the next time a similar task ships and the skill catches the thing, unprompted — not when it describes the gap eloquently. Two further markers tell you it's real. First, a reader who knows your codebase reads the SKILL.md and says "yes, that's the convention" — because it encodes a real, named convention from your session, not a generic best-practice a manual could have written. Second, you can name the move in one sentence; if you can, that's the proof, and no further articulation is owed. The negative test is the sharp one: if the file describes the gap but you still find yourself hand-correcting the same behaviour next run, you've written documentation, not a session-shaper — re-scope it in conversation and try again.

Use when

You've run the same kind of task twice, the second run still tripped on something the first one warned you about, and you're about to fix the diff and move on — leaving the lesson nowhere. Also fires when a verifier stayed silent on a drift it should have caught, or when you notice you're hand-correcting the same agent behaviour session after session.

Why
The principle

test → learn → encode. The skill is the memory your future self doesn't have to re-earn.

"The loop closes when the lesson ships — until then you've just had a good idea twice."

A scaffold catches only what it was shaped to catch. The gaps that surface after two runs aren't proof the scaffold failed — they're data it couldn't have anticipated, and the only way that data compounds is if it leaves your head and becomes a thing the next session reads cold. A skill authored from two real runs arrives with an authority a principles-derived rule never has: your codebase taught it, not a manual.

The encode phase is the one everyone skips, because by then the bug is fixed and the satisfaction is spent. The compound-engineering frame names the cost of skipping it — a frame Kieran Klaassen has put plainly: each unit of work should make the next one cheaper, and it only does if the lesson ships as an artefact the next agent inherits. The mechanism is brutally simple. The skill is the move you don't have to re-discover.

A lesson you remember is ephemeral. A skill that fires is durable.
