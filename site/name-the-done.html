Name the done before you dispatch

The principle: a task is only as dispatchable as its done is checkable — the bottleneck isn't the agent's stamina, it's your willingness to commit a finish line.

Before you send an agent off to run for hours, state a done you can check in one sentence, then decide out loud whether this is a send-off (a checkable finish, packaged enough to run on its own) or a nudge (step-by-step work you'll babysit). The sentence is the deliverable — not the dispatch.

The mechanism · why a long run runs at all

The bottleneck isn't the agent. It's the sentence you skipped.

Here's the unglamorous truth about long-running agent work: the thing that decides whether the next four hours happen with you or without you is not the agent's stamina. It's whether you committed to a finish line before you pressed send. You point a capable agent at a migration, a gnarly refactor, a test-coverage push — and twenty minutes in you're answering questions, correcting paths, re-explaining the goal. You've become the agent. The diagnosis is almost never that the model ran out of road. It's that you dispatched something you never gave a checkable done, so it had nothing of its own to steer toward and you had nothing to check it against.

Watch the same task split in two depending on one variable. Send "modernise the auth module" and the agent has no destination — so it asks, and you narrate, and the whole value of an async tool collapses back into synchronous babysitting. Send "auth reads its config from the new provider, the existing suite stays green" and there's a target the agent points at and a thing you can check on return — without re-reading every line it wrote. Same backlog item. Same agent. The difference is one sentence, written before the dispatch, not after.

We resist naming the done because naming it feels like premature commitment — what if the shape changes mid-run? So we dispatch vague intent and tell ourselves we'll "stay close to steer." That instinct is exactly backwards. The done isn't a contract you must hit first try; it's a steering target — the thing the agent points at and the thing you check the trace against. Stay-close-to-steer is how a four-hour async capability quietly becomes a four-hour synchronous chore. Commit the finish line to a sentence and the run gets to happen without you narrating each step.

A vague intent doesn't make the agent dumber. It removes the only thing it could have aimed at.

The deliberate cut · send-off or nudge

Decide the mode out loud — send-off, or nudge.

Naming the done buys you a second, sharper move: the send-off / nudge cut. A send-off has a checkable done and enough context to run on its own; a nudge is step-by-step work you'll deliberately sit in for. Both are legitimate — some work genuinely wants your hand on it. The trap is dispatching a nudge as if it were a send-off, then feeling betrayed when it needs babysitting. That's where the resentment comes from. Naming the mode up front sets your own expectation, so a hands-on run feels like a choice rather than a failure.

The cut has a second axis: size. Reject the typo-fix — the agent crunches it in one shot and you learn nothing about its reach. Reject the quarter-long epic — it won't cohere over a long crunch window, and you'll spend the whole run re-anchoring it. Aim for the slice in between: a real piece of work that genuinely needs sustained coherence, requirement-weaving, and multi-file reasoning — the properties that make something a long-running task rather than a one-shot. One reframe unlocks the willingness to dispatch at all: every send-off is an experiment, not a production run you need to get right the first time. The done is the steering target you point the experiment at — not a deliverable you're contractually bound to. Stopping a run when you've seen enough is reading, not failing. That distinction is what lets you press send instead of polishing the prompt forever, waiting for a certainty that never arrives. The first done you write will be the hardest one you ever write, precisely because you're treating it as a contract when it's only a target.

The compounding loop · the next done gets easier

Each dispatch teaches you what a nameable done feels like.

The loop below closes the way good habits do: name the done · dispatch · read the trace against it · the next done gets easier to name. Every dispatched task teaches you what a checkable finish line feels like on your own codebase — which slices cohere over a long window, which dissolve into questions, what a stranger needs in the sentence to check it. Your scoping sharpens run over run. The teams that under-invest here keep re-learning the first lesson on every task; the operators who treat the done as a reusable skill compound it. Boring on day one; a different relationship with your backlog by day thirty.

What "Test" actually means · in practice

The done is named when a stranger can check it.

The test for a named done is not "sounds clear to me" — you wrote it; of course it does. It's the read-back test: hand the one sentence to someone who hasn't seen the task and ask them to state what "finished" looks like. If they come back with "finished by what measure?", the done isn't named yet — it's still living in your head, not in the sentence. The harder test arrives on return: when the run reports back, can you check it against the done, or only against the agent's own summary? If the only evidence you have is the model's cheerful "shipped most of it, hit a snag on X," you named a vibe, not a done. RLHF-trained models will frame partial failures as partial successes — so a real done has to be checkable independent of the agent's self-report. And the live tell: if you catch yourself re-explaining the goal mid-run, the done was never named. That's the negative test, and it fires whether you wanted it to or not.

Use when

You've got an agent that could run for hours unattended, and a backlog you keep meaning to hand it — but every attempt turns into you typing every step. The async capability has outrun your scoping habit.

Build

A one-sentence done written where the dispatch and your future self can both read it, an explicit send-off-or-nudge call, and a sized slice — neither typo nor epic.

Test

A stranger reads the sentence and says "that's what finished looks like."
Not merely "sounds clear to me."

Why
The principle

A task is only as dispatchable as its done is checkable.

"An agent can run for hours unattended. Whether it does depends on one sentence you write before you start."

The counterintuitive bit: the bottleneck on long-running agent work is not the agent's capability — it's your willingness to commit to a finish line before you begin. We dodge naming the done because it feels like premature commitment, and that dodge quietly collapses an async agent back into synchronous babysitting. Reframe the done as a steering target, not a contract, and the resistance dissolves: you're not promising an outcome, you're giving the run something to aim at and yourself something to check it against.

The send-off-vs-nudge cut is the same insight stated as a decision: some work wants your hand on it; the skill is knowing which, and refusing to babysit the work that didn't. Naming the done is the cheapest possible move — one sentence — and it's the one that determines whether the next four hours run with you or without you. Everything downstream assumes it: you can't walk a system against a task you can't state, and you can't package a run whose finish you can't check.

Where it sits: at the personal layer this is a scoping habit. At the team layer a one-sentence done is the unit a teammate can pick up, check, or hand back without re-deriving intent. At the company layer the named done becomes the interface between human intent and unattended agent runs — how an organisation turns a backlog into dispatchable work. An org's ability to run agents unattended is gated on whether its work is routinely scoped to a checkable done; this card is the precondition the rest of the Intent → Context → Work chain rests on.

The agent has the stamina. The sentence is what's missing.
