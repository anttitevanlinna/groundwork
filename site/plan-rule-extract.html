Mine the plan for rules

The principle: structure is persuasive — a plan looks like a decision even when it's a draft, which is exactly why the reasoning you used to shape it is worth more than the plan.

Right after you approve a plan and before you touch the diff, read the session back and harvest the decisions you made into a small file the next plan reads cold — so the judgement that usually evaporates with the tab becomes a rule that fires next time, and at company scale becomes the spec a backlog-triage agent reads.

The plan and the diff get shipped. The judgement gets saved — to a file that reads itself back next time.
The mechanism · the part you already paid for

The plan was the cheap bit. The reasoning was the expensive one.

Watch where the attention actually goes in a planning session. Not into the plan text — Claude drafts that in seconds. It goes into the decisions you make against the draft: this task is worth planning and that one isn't; split the checkout work off the epic so one branch ships alone; flag the migration step as soft; reject the code-first default because this repo wants tests first. That judgement is the costly part, and it's the part that evaporates fastest. The moment you hit approve, all of it lives only in a transcript you will almost certainly never re-read.

The honest tell is the gap the curriculum names plainly: templates stay generic; this file carries your rules. A blank task-shaping template gives you tidy advice nobody's actual working style ever matched — “pick tasks that span multiple files,” that sort of thing. The rules you really used to shape this task on this codebase only exist in the scrollback until you pull them out. The move isn't to write a playbook from a blank page. It's recognition, not authoring: the judgement is already on the screen, sorted into chat. You just sort it into a file.

Once the three-to-five rules are on the page, do the one thing that separates a real harvest from a tidy summary: rewrite or reject at least one before you save it. The rule that arrives generic is the one that needs your hand on it. “Pick tasks that span multiple files” came from nowhere in particular — it's the kind of advice a template would have given you for free. So either make it name a moment from this session (you split checkout off the epic because one branch could ship without the migration) or cut it. The pause where Claude hands you the draft and you push back is not friction; it is the engagement step. A rule you can't trace to a moment in the scrollback is generic by definition.

The location decision · from disk to firing

Where it lives is when it fires — not a folder preference.

Here is where most attempts quietly fail, and it feels like progress while it does. You harvest beautiful rules, save them to a notes folder, and feel done. But the dimension that matters isn't tidiness — it's when the rules fire. Two paths auto-load at cold start: ~/.claude/CLAUDE.md fires anywhere on this laptop; ./CLAUDE.local.md fires only when this repo is open. Anywhere else — a notes folder, ~/.claude/memory/task-shaping.md — sits silently on disk until something reads it. And if you pick one of those non-auto-load paths, you have to wire the import yourself: @~/.claude/memory/task-shaping.md added to a file that does auto-load. Naming a path is not the same as wiring it. That import line is what makes “fires anywhere on this laptop” actually fire — and it's the move's most-skipped beat.

Process diagram · 02State two is the silent trap: a rule on disk with no @import is a rule the agent never reads — capture without firing isn't capture.

One last beat, and it's a discipline more than an action: name the leverage horizon, then stop. Ask Claude how this same file could drive automated task-splitting later, and you'll hear three plausible shapes — a Slack thread that triages an incoming request, a GitHub issue event that pre-factors the work, a once-a-sprint read of the backlog. Ask for the shapes, not the code. These are named possibility shapes the file could later drive, not capabilities anyone is building or claiming today; today is capture, application is downstream. It's the same “approve, don't execute” restraint you just used on the plan, applied one layer up: save the rule, don't ship the bot. If you started writing the Slack triage, the move overshot. (And the runtime, when one of these does ship, is an external app or workflow calling an agent — not Claude Code living inside Slack.)

The compounding loop · what changes between passes

Each planning session makes the next one cheaper to read.

The diagram below closes the thread. You run a plan session; you mine the rules; you rewrite the generic one; you save it to a firing location. Then the next plan opens with the file already in context — so it arrives pre-shaped, the agent needs fewer push-backs to land, and the new decisions you do make become the next harvest. This is the Block-1 move at the planning grain: observation becomes a rule. We borrow the framing from Huryn's three-block memory — a frame for naming what you've built, not a template to fill in — to say what this file collects. Each lap, the task-shaping file carries more rules and the next plan starts further along. Boring on the first session; dominant by the tenth.

What "Test" actually means · in practice

The test is whether you can name the moment.

The check isn't “does this read well” — a stranger would call any tidy rule file polished. The check is whether you can read each rule aloud and name the session moment that produced it. If you can't, it's generic, and generic is exactly the thing a blank template hands you for free. Run the same test on the firing mechanism: the file is at an auto-load path, or you can point at the @import line that wires it in — otherwise it's a rule you wrote and the agent will never read. And the last check is a restraint check: you named at least one automation shape and didn't build it. If you started writing the Slack bot, the move overshot into application — these are downstream shapes you name, not a bot you build in this move.

Why
The principle

Structure is persuasive — a plan looks like a decision even when it's a draft. So keep the reasoning, not the draft.

"The plan evaporates; the rules you used to shape it shouldn't."

The counterintuitive bit: the valuable artefact isn't the plan, and it isn't the diff — it's the rules you used to shape them. A blank task-shaping template produces tidy generic advice nobody's working style ever matched. A file mined from a real session produces rules that recognise the next task because they were born from the last one. Same observation→rule move you'd make on any session, run at the planning grain.

And the location discipline is where most attempts quietly die. A rule that doesn't auto-load, or isn't @import-wired, is a rule that fires never — which feels like progress and isn't. Capture without firing isn't capture.

Where this sits · personal → team → company

At personal scope this is the harvest that turns one planning session's judgement into a firing rule. At team scope the same task-shaping file becomes a shared spec — how your team factors work, written down instead of re-explained. At company scope it's the steady spec a backlog-triage agent reads on every Slack thread, issue event, or sprint cadence — so how the org factors work stops living in each engineer's head and becomes a guardrail the whole intake runs against. (Positioning, not a coined law — and those automation shapes stay named, not built, until that's a downstream conversation.)
