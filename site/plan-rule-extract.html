Mine the plan for rules

The plan was dictation. The rules it contained are already in the transcript — the only question is whether you publish them to a zone a session can reach, or leave them in a notebook no resolver ever queries.

The query that fires cold

Every session opens with a lookup

Each time a session starts, the agent runs something close to a DNS lookup: it reads the files that auto-load, takes whatever records are present, and begins from there. A rule in ~/.claude/CLAUDE.md — the laptop-wide zone — resolves in every session on the machine. A rule in ./CLAUDE.local.md resolves only when this repo is the working directory: the authoritative zone for that one subdomain. But a rule sitting in a notes folder — ~/notes/task-shaping.md, ~/.claude/memory/planning-rules.md — returns NXDOMAIN. No record found. The session starts cold. The rule existed on disk; it was never published to a zone any query reaches.

That is the failure this card addresses. Not forgetting to capture — publishing without checking that the record resolves. A rule can be captured the moment you write it down and stay unpublished forever, and the gap between those two states is invisible until a cold session needs it and comes back empty-handed.

The publishing window

The session after a plan is the dictation room

A plan session produces something more valuable than the plan: the reasoning you used to shape it. You decided this task was worth planning and that one wasn't. You split the checkout work off the epic because one branch could ship independently of the migration. You pushed back on code-first because this repo runs tests first. That judgement is already dictated — it sits in the scrollback. The plan was the cheap output; the shaping decisions are the expensive content, and they evaporate fastest.

So enter after the plan is approved, while the tab is still open. You are not authoring here. You are recognising. The rule is already in the chat; your job is only to address it. Scan the session for the three to five moments where you pushed back, split something, or rejected a default that wouldn't survive this codebase. Write each as a rule — short, specific, pointing at a moment. “Split when one branch can ship without the rest” beats “prefer small tasks.” The first traces to a decision; the second is a template wearing a name.

A plan session is a recognition room, not a writing room. The rule was decided live — you are only naming the address it should resolve at.
The resolution radius

Pick the zone the rule should resolve in

Once the rules are drafted, the question is scope: where should this rule resolve? There are two authoritative answers — not a sorting table, just a radius choice. A rule resolves machine-wide or it resolves for one repo, and you pick which.

Authoritative zone
~/.claude/CLAUDE.md
Resolves in every session on this machine. Rules that hold across repositories: how you want plans structured, what makes a task worth plan mode, your defaults for splitting work.
radius: laptop-wide
Repo subdomain
./CLAUDE.local.md
Resolves only when this directory is open. Rules bound to this codebase: the test-first requirement, the branch conventions, the edge cases this service keeps hitting.
radius: this repo only
The dead letter

Anywhere else resolves never. A file that doesn't sit in one of those two auto-load paths — and isn't explicitly imported into one — doesn't exist at session start. It is the IP address you wrote in your notebook: correct, reachable in theory, invisible to every resolver that matters. The cold session asks for the rule and gets NXDOMAIN back.

The most-skipped beat — wire the record

If you want the rule in a separate file — because you have many, or you're building toward a shared kit — you can keep it there. But then you must wire the import. An @-reference inside an auto-load file is the delegation record: for this zone, look up that file. Naming a path is not the same as wiring it — the import line is the beat that most looks like a detail and most often gets skipped, and it is the one that turns a note into a published record.

# the rule lives in its own file (fine) — but on its own it is NXDOMAIN
~/.claude/memory/task-shaping.md  # not auto-loaded

# wire it into the zone that resolves — one line publishes the record:
# inside ~/.claude/CLAUDE.md
@~/.claude/memory/task-shaping.md  → now resolves at cold start
How you know it fired

Verify in a fresh session, not in your head

The test is blunt, and it must run in a session that has loaded nothing from this one. Open a new session in the relevant directory and ask the agent to describe the constraints it's working under for plan-mode tasks. Make it recite. If it reads back the rules you just wrote, the record resolves — the rule is published. If it starts from a blank baseline, you have NXDOMAIN: the rule is on disk somewhere, but in no zone the session queries. Believing it resolved is not the same as watching it resolve.

Test — cold-start recite

Open a fresh session. Ask the agent to state its plan-mode constraints before you give it any. Two outcomes, and only one of them means you shipped:

recites the rule Resolves. The record is published. The rule will fire on every cold start in this radius, with no prompting from you.
blank baseline NXDOMAIN. Captured, not published. The rule is on disk in the wrong place — move it to a zone file, or wire the @import.
Why this is the delivery problem

Capture feels like the work; it isn't

Rules are cheap to write. The trap is that writing the rule down feels like the work is done — so most practitioners treat capture as the terminal step and stop one move short. DNS makes the error legible: you can have perfect knowledge of the correct address and still be unreachable, because knowing an IP and publishing it to a zone any query can find are genuinely different steps. Capture is knowing the address. Delivery is publishing the record. The whole card lives in that gap.

Why — the belief underneath
A rule that resolves is infrastructure. A rule that doesn't is a note to yourself.

A move only counts when it crosses the wall — and a rule crosses the wall the moment a session other than the one that wrote it can reach it. Until then it is private knowledge wearing the costume of leverage. The delivery step is the give-it-away step, scaled down to a single file: publish the record and every future session inherits it for free; leave it captured and you re-decide it cold, every time, forever.

This is why recognition beats authoring in the plan room. The expensive thinking already happened; refusing to publish it is the most common way to feel productive while delivering nothing.

This week — deliver one record

Take the last rule you captured — from a plan session, a push-back, a sprint retro, wherever it landed. Ask two questions: where does it live, and will it fire next time?

If it sits in ~/.claude/CLAUDE.md or ./CLAUDE.local.md already, it resolves — you're done. If it lives anywhere else, decide its radius and move it there, or add the @import that wires it into a file that auto-loads. Then open a fresh session and make it recite. Delivery, not capture.

The tab is about to close. Publish the record before it does.
