Write the failing test first

The principle: claims aren't evidence — an agent's "fixed it" is a story; a red-then-green test is the only thing that can't confabulate.

Before the agent touches code, make it write the test that fails for the bug's reason — watch it go red — then let it fix until the test goes green. The personal habit fences the agent's fluency at your own keyboard, and the same test becomes the gate every later PR has to clear.

A green diff is a confident claim. A test that went red first is the only proof the bug existed.
The mechanism · claim vs. evidence

Two paths from the same bug.

Hand a coding agent a bug and it does the natural thing: reads the symptom, nods, and starts editing — fast, plausible, unverified. The diff that comes back reads right. It compiles. It probably even runs. And that is exactly the trap, because a fix that reads right is not a fix that is right, and the agent's fluency is most convincing precisely where it's wrong. Its self-report — "fixed it, here's why" — is a reconstruction after the fact, not an observation. You are one "looks fine" away from merging a change whose only proof is that it didn't error.

The same bug can take a second path that ends somewhere very different. Before any code changes, the agent writes the test that reveals the bug, runs it, and you watch it fail — red, for the reason you'd expect. Then it fixes the root cause and runs again — green. Same input, same agent. The only thing that changed is that one path produced an artefact that could have said no. A test that fails first and passes after can't confabulate: it either reproduces the bug or it doesn't. The picture below puts the two paths side by side.

The instruction is one sentence, and the order inside it is the whole pattern: write the test that reveals this bug, run it, confirm it fails the way you'd expect, then fix the root cause and run again. The middle clause does the work. A test that fails for the wrong reason is worse than no test — it green-lights with a typo in the assertion, a wrong import, a fixture that never reached the code. So you watch the red, and you check it's red because the bug is real, not because the test is broken. Only then is the green meaningful.

A test that fails for the wrong reason is worse than none. Watch the red — and check why it's red.

Resist the urge to dress this up. On a trivial bug, plan mode is overhead, not safety — ceremony you reach for because it feels like rigour. The discipline that actually earns its keep on a small bug isn't a plan; it's the failing test. And the temptation runs the other way too: when the fix is "obvious" you want to skip the test entirely. Obvious is exactly when the agent's guess compiles and ships. The smaller and more boring the bug, the cheaper the test, and the more often you'd otherwise wave it through on a glance.

The upgrade · rubber-stamp → interrogated

From the 30-second nod to the diff you argued with.

Writing the test is half the move; reading the diff is the other half, and it's a separate discipline. The brittle version is the rubber-stamp — the agent shows a change, you say "looks fine" in under thirty seconds, and you've tested the agent's confidence, not the code. The upgraded version is interrogated: you read the diff line by line, quote the one line you'd have written differently and say why, and let the better argument win — yours or the agent's. Then you push once on depth: is this the root cause, or a layer above it? The first cut usually fixes whatever makes the test pass; the deeper cut asks whether the test pointed at the right thing at all. Ask what a deeper edit would touch, and watch what the agent defends.

Process diagram · 02The accept upgrades from a glance to an argument: read · quote one line · push on root-cause-vs-surface · optional second pass on the deeper layer.

One trap is built into the loop itself. An agent under pressure to go green can write a test that passes vacuously — asserting nothing, or asserting something that was already true. It looks like coverage; it covers nothing. The guard is the same red you already insisted on: the test must fail first, and fail for the bug's reason. If it's green on the very first run, you didn't gain a test — you gained a decoration. This is why "watch it fail" isn't a nicety; it's the one check that catches a faked test before it becomes permanent false comfort in the suite.

The compounding loop · the suite gets richer

The test you wrote today catches the regression you'd re-debug next month.

Here's where the move stops being a one-off and starts paying interest. Each closed loop — bug, failing test, fix, passing test — leaves the test behind as permanent regression cover. The next change runs against it for free. Do this a hundred times and the suite isn't a chore you maintain; it's a hundred bugs that can no longer come back without tripping an alarm. The loop closes back through the codebase, not as a ritual you perform — the test you wrote for today's confident-but-wrong fix is the one that catches the silent regression you'd otherwise re-debug, from scratch, next month.

Use when

You're about to hand an agent a bug and it's already drafting the fix — a backlog bug you half-remember, a wrong-total or off-by-one you can't eyeball, a change touching a file you didn't write. Anywhere agent speed outruns your ability to check it.

Build

A failing test committed before the fix — the bug's evidence, now permanent regression cover — and a shipped PR whose history shows test-before-fix, plus a diff you objected to at least once.

Then it's a habit, not a task: compound interest on a test suite. Each loop fences one more bug for good — and converts the agent's fluency from a risk into reviewable evidence.

Monday move: take the next bug an agent offers to fix. Before it touches code, send one line — "Write the failing test that proves this bug exists, run it, show me it fails — then fix the root cause." Needs nothing but a different first sentence: no platform, no budget, no sign-off. No test infra on this path? Log "no verifier here" as a real finding — the gap surfaces later, it isn't a blocker now.

Why
The principle

Claims aren't evidence. The agent's fix is a hypothesis; the failing test is the only thing that makes it falsifiable.

"Without a failing test first, the fix isn't a fix — it's a guess that happens to compile."

An agent's self-report is a reconstruction — persuasive precisely where it's wrong. A test that fails first and passes after is the one artefact in the loop that can't confabulate. It either reproduces the bug or it doesn't. You already know TDD; the second discipline is what's new — running it with an agent means the test also fences the agent, converting its fluency from a risk you absorb into evidence you can review.

The counterintuitive part: on a trivial bug you're tempted to skip the test because the fix is "obvious." Obvious is exactly when the agent's guess compiles and ships. Calibration helps here too — the curriculum's rule-of-thumb is to assume roughly a tenth of what the agent says or does is misrepresentation. The failing test is how you stop guessing which tenth.

⚠ Calibration, not measurement

"Assume ~10% of what the agent says or does is misrepresentation" is an illustrative calibration figure the curriculum uses to set skepticism — not a measured error rate. Could be more, could be less. It justifies the habit; it doesn't quantify the risk.

A green diff is a claim. A red-then-green test is evidence.
How you KNOW it worked · in practice

The test went red before it went green — you watched it fail for the right reason, not pass on the first run. A line-level objection sits in your scrollback or the commit body before the merge: proof you read the diff, not skimmed it. And the root-cause turn actually happened — a "is this the root cause or a layer above?" exchange before any commit.

The negative test is the honest one: if the agent's first answer went straight to green and you said "looks fine" in under thirty seconds, you tested the agent's confidence, not the code. No red, no objection, no depth question — no evidence.
