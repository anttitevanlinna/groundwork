Write the failing test first

The contrarian read: the rigour you reach for is the wrong one. On a small bug you grab plan mode for safety — but the only thing that proves the bug existed is a test you make go red on purpose.

A surveyor sets a datum mark in the ground before a single wall goes up — every later measurement is taken from it. Your equivalent is a test the agent writes and you watch fail for the bug's reason before any code changes; without that mark, the green diff that follows is a guess that merely compiles. Set the mark before you build.

Here's the move most people get backwards: ground truth on a bug isn't something the agent reports to you — it's something you set yourself, first, in the ground. Hand a coding agent a bug and it does the natural thing: reads the symptom, nods, starts editing. The diff reads right, compiles, probably runs. None of that is proof. The agent's self-report — "fixed it, here's why" — is a reconstruction after the fact, persuasive precisely where it's wrong. The only artefact in the loop that could have said no is a test you make go red on purpose, before a single line changes.

The instruction is one sentence, and the order inside it is the whole pattern: write the test that reveals this bug, run it, confirm it fails the way you'd expect, then fix the root cause and run again. The middle clause does the work. A test that fails for the wrong reason — a typo in the assertion, a wrong import, a fixture that never reached the code — green-lights nothing; it's a mark set on sand. So you watch the red, and you check it's red because the bug is real. Only then is the green you get later worth anything. What that one closed loop writes into the run reads like this:

The test doesn't get torn down with the scaffolding. It stays as the bug's evidence — and the next change runs against it for free. Do this a hundred times and the suite is a hundred bugs that can't come back without tripping an alarm.
The words in the agent's summary never changed. One run produced a mark that could have said no — which is the entire difference between a claim and evidence.

A test that fails for the wrong reason is worse than none. Watch the red — and check why it's red.

Now the contrarian bit, stated plainly: on a trivial bug, plan mode is overhead dressed as safety — ceremony you reach for because it feels like rigour. The discipline that actually earns its keep on a small bug isn't a plan; it's the failing test. And the temptation runs the other way too — when the fix is "obvious" you want to skip the test entirely. Obvious is exactly when the agent's guess compiles and ships. The smaller and more boring the bug, the cheaper the mark, and the more often you'd otherwise wave it through on a glance. The loop compounds without you noticing: each closed pass leaves a datum behind, so the bug you fenced today is the silent regression you'd otherwise re-debug, from scratch, next month.

⚠ Calibration, not measurement

The curriculum's rule-of-thumb is to assume roughly a tenth of what the agent says or does is misrepresentation — an illustrative figure to set skepticism, not a measured error rate. Could be more, could be less. The failing test is how you stop guessing which tenth. It justifies the habit; it doesn't quantify the risk.

your standing order · from monday

Take the next bug an agent offers to fix — a backlog bug you half-remember, a wrong-total or off-by-one you can't eyeball, a change touching a file you didn't write. Before it touches code, set the mark. It needs nothing but a different first sentence — no sign-off to chase, just a line you'd have typed anyway:

"Write the failing test that proves this bug exists, run it, show me it fails — then fix the root cause."

Then read the diff against the mark: object to one line, ask whether it's the root cause or a layer above, and let the better argument win. That objection in your scrollback is the receipt you read the diff rather than skimmed it.

No test infra on this path? Log "no verifier here" as a real finding — the gap surfaces later; it isn't a blocker now. And this is the team move too: a PR whose history shows test-before-fix is a mark anyone downstream can re-measure from, long after the agent's confidence has been forgotten.
