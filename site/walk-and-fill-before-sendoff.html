Walk the system against the task

The principle: the system you have is what gets tested — not the one you meant to build.

Take the context you've accumulated, walk it against the one real task you're about to send off, fill only the worst few gaps, and let the agent run against your system as it stands — so the return teaches you what's actually missing, not what you imagined. This is a personal habit that keeps a whole company's memory honest at scale.

You didn't patch the system clean. You load-tested it — filled the worst three, left two open on purpose, pinned the SHA, let it run.
The mechanism · what a real task makes visible

A gap is invisible until a specific load walks over it.

You already have a context system. Not a tidy one — a CLAUDE.md, a CLAUDE.local.md, a folder of observations, an ADR or two, a skill you authored last week. Each was written in its own moment, to fix the thing in front of you that day, and none of it was ever measured against the task you're about to send off. Read cold, the pile looks ready. That's the illusion: completeness is a property a context system only appears to have until something real leans on it.

The shorter loops sit behind you — a bug fix, a plan read, work where you stayed in the loop. This is the first long one: multi-hour, sustained, running without you watching. And the move that decides whether it's worth your while isn't writing more rules. It's walking the system you have against the system the task needs and seeing, for the first time, which lines are load-bearing for this work and which slots are simply empty. The files don't change in the walk — the task does the X-raying. The diagram below is the same pile twice: ready-looking on top, X-rayed by one named task on the bottom.

Walking is a job you can hand to a subagent. Point one at your CLAUDE.md + CLAUDE.local.md + memory + ADRs + any skills and connectors, and have it walk them against what this task needs. It returns a ranked gap list. The trap here is reverence: the audit is a hypothesis about your system's holes, not a verdict you clear. Push back on it exactly the way you'd interrogate any read — it over-weights the tidy gaps it can name and misses the assumption baked so deep nobody wrote it down. You're the one who knows which hole will actually hurt this run.

Walk the system you have against the system the task needs. The empty slot is the gap.

The discipline · over-prepared loses to deliberately under-filled

Fill the worst three. Then stop on purpose.

Here's where almost everyone's instinct fails them. The audit hands you five gaps and every nerve says close them all — give the agent its best shot. Resist it. Fill the worst three; leave the rest open, and write down which two you're leaving and why. The skipped gaps aren't laziness — they're the instrumentation. A system patched until it looks complete can't tell you what it was missing, because you erased the evidence before running the test. Under-filling on purpose is what lets the return surface what genuinely breaks. The diagram below draws the two paths to a send-off, and which one actually teaches.

Process diagram · 02Patch it clean and the return goes quiet. Under-fill on purpose and the run breaks where you can read it. Three is a deliberate teaching budget for the experiment — not a measured rule.

One trap is sharp enough to name on its own. You'll spot a thin place, decide "that's a real code change, I'll skip it," and the un-packaged run fails in a boring way — wrong DB assumption, stale config — instead of an interesting one. If the audit calls it context, it's context, even when the fill is just one rule ("we use Postgres, not Mongo"). A boring failure teaches nothing; the agent lost coherence on something you'd have caught in ten seconds. The whole point of the run is the interesting break — the one only the next move can diagnose. Don't defer a contextual gap because the fill looks architectural.

Then send it off un-packaged, in the same session: no plan.md, no verifier, no reference artefact. Pin the starting point first — commit current state on a feature branch, record the SHA and the transcript path — then dispatch the scoped task with your rules, memory, ADRs and skills loaded, and let it run. One caveat has to travel with that word: un-packaged here is a deliberate first step to expose failure modes — packaging is the right move once you've seen what un-packaged gets wrong, not a thing to skip. You're not shipping a production run you owe a clean result. You're running an experiment. The trace is the data.

The compounding loop · evidence over anticipation

Each lap, the gaps you fill are the ones real runs surfaced.

The picture below closes the thread. Scope one task, walk the system as an audit, push back and pick the worst three, fill those and pin the SHA, send it off un-packaged, read the return, then sharpen the gaps the run actually exposed — and scope the next task. Each pass the context carries a richer, evidence-fed system, and the holes you close are the ones a real load found, not the ones you imagined at the desk. That's the difference between a habit that compounds and a policy nobody's work ever validated.

What "Test" actually means · in practice

The honest test is the gap you can name out loud.

You'll know the move worked not by a green check but by what you can say. You can name the one task in a sentence, and its 'done' is concrete — neither a typo-fix nor a quarter-long epic. The audit returned a ranked list and you picked exactly the worst few, filled those, and can say out loud which gaps you're deliberately leaving open and why. At least one fill was a contextual gap you were tempted to defer as "architectural" — you filled it anyway, even if the fill was one rule. And the starting point is pinned: git log shows a feature branch with a "starting point" commit before the agent's first task commit, with the SHA and transcript path noted somewhere you'll find later. The negative test is the tell: if you closed every gap you could find, you over-prepared and the return will teach you nothing; if you packaged it, you pre-empted the lesson. The un-packaged failure is the data.

Use when

A real send-off task is in front of you — a migration, a gnarly refactor, a test-coverage expansion, an API cutover — and you don't actually know whether the context you've built will carry it, or where it'll quietly fall through.

Build

A load-tested context system pinned to a comparable starting point: two or three run-tied fills, a business-rules pointer wired or the gap named, a starting-point commit at a recorded SHA — plus the running task itself.

Why
The principle

The system you have is what gets tested — not the one you meant to build.

"Fill the worst three; send the rest un-packaged — the gap you leave open is the one the run will teach you."

Every instinct says prepare thoroughly: close every hole the audit finds, give the agent its best shot. But a system patched until it looks complete can't tell you what it was missing, because you erased the evidence before running the test. Gap analysis is walking the system you have against the system the task needs — and the only honest way to find the gap is to let the real load find it for you.

The trap inside the trap is the contextual gap dressed as architecture. Defer it and the run fails boringly, on a wrong assumption you'd have caught in seconds — which teaches nothing — instead of failing interestingly, where the agent loses coherence in a way only the next move can diagnose. Treat the send-off as an experiment, not a production run you owe a clean result. The trace is the data.

Filling fewer gaps teaches you more.
Read these as labelled, not literal

"Three" is a deliberate teaching budget for a first un-packaged run — not a measured optimum. The point is to under-fill on purpose so the run can teach you; there's no law that filling three gaps maximises learning.

"Un-packaged" is a sequencing choice, not a claim that un-packaged runs are better — it's a deliberate first step to expose failure modes. Packaging is the right move once you've seen what un-packaged gets wrong, not a thing to skip.

The three-block frame the walk leans on — Huryn's three-block memory — travels as a frame for naming what you've already built, not a template to fill in. It makes an empty slot legible; it is not a checklist to author against.

Where this sits · personal → team → company

This is the personal-layer habit that keeps a context system honest at scale. An individual who walks and deliberately under-fills produces evidence-fed gaps instead of imagined ones — and that same discipline, test against a real load and fill from what the run exposed, is exactly what keeps a team's shared kit and a company's memory layer growing from real failures rather than prophylactic policy no one's load ever validated. The un-packaged failure here is also the prerequisite that teaches what the next move — packaging the run — has to carry.
