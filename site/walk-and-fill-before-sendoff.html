Pre-sendoff gap-audit

The principle: the system you have is what gets tested — not the one you meant to build.

A field scientist leaves rows of the plot untreated on purpose — those bare strips are the only thing that can tell her what the treatment actually did. Same move, on context: before you send an agent off on a long run, have a subagent rank your CLAUDE.md, memory, ADRs and skills against the one real task, fill the worst three gaps, and leave the rest open on purpose — so the run reads them for you instead of your imagination.

You didn't patch the context clean. You ran a trial — filled the worst three, staked two open on purpose, pinned the SHA, let the run find the rest.
A context you filled everywhere tells you nothing

That bare-row trick is the whole pattern; the rest is plain agent mechanics. You already have a context system — a CLAUDE.md, a CLAUDE.local.md, a folder of observations, an ADR or two, a skill you authored last week. Each was written in its own moment, to fix the thing in front of you that day, and none of it was ever measured against the task you're about to send off. Read cold, the pile looks ready. That readiness is the illusion: a gap in context is invisible until a specific run leans on it. The first long send-off — multi-hour, sustained, the agent working without you watching — is the load that finally walks across the whole window at once and shows which lines are load-bearing for this task and which slots are simply empty.

Here's the part worth sitting with: over-preparing and pasting-and-hoping fail the same way. Close every gap the audit names and the run returns clean and tells you nothing — there was no open slot left to read the result against. Send the window as-is and you can't separate a real context failure from your own neglect: every slot is empty, so no single one is diagnostic. Both erased the control. The empty slot you leave on purpose, named in writing, is the one thing that turns the run from a delivery into a measurement.

The gap you leave open isn't a defect to close. Staked on purpose, it's the only instrument you've got.

The gap-audit · patch vs. trialFill every gap and the run is fine and silent. Stake two slots open and the agent breaks where you can read it. Three fills is a deliberate teaching budget — not a measured optimum.
Scope one task, stake two gaps, send it off

Run it Monday. Pick one task off your backlog you've meant to hand an agent — multi-hour, real, a done you can say in a sentence. Not an epic, not a typo-fix. It has to be specific enough that a single run will exercise the whole context window at once. Then point a subagent at your CLAUDE.md · CLAUDE.local.md · observations · ADRs · skills and have it rank where the context runs thin against that task. It returns a ranked gap list — and the trap is reverence. Push back: the ranking is a hypothesis about your holes, not a verdict you clear. It over-weights the tidy gaps it can name and misses the assumption baked so deep nobody wrote it down. You're the one who knows which one this task will actually hit.

Fill the worst three — and watch for the one trap sharp enough to name. A gap will look like "a real code change, I'll skip it", and if you skip it the run fails in a boring way: wrong DB assumption, stale config, something you'd have caught in ten seconds. If the audit calls it context, it's context, even when the fill is one rule ("we use Postgres, not Mongo"). The whole point of the run is the interesting break — the one only your next move can diagnose. Then the two gaps you're leaving: stake each one in writing, with why. Those notes are the instrument.

Now pin the starting point — commit current state on a feature branch, note the SHA and the transcript path — and dispatch the scoped task in the same session, un-packaged: no plan.md, no verifier. Let it run with your rules, memory, ADRs and skills loaded as they stand, and walk away. When the trace comes back, read it against the slots you staked open: next time you fill the gaps a real run surfaced, not the ones you imagined at the desk, and your context carries a richer, evidence-fed load into every send-off after.

The two staked gaps · read these as labelled, not literal

Three is a deliberate teaching budget for a first un-packaged run, not a measured optimum. Under-fill on purpose so the run can teach you; there's no law that filling three gaps maximises learning.

Un-packaged is a sequencing choice, not a claim that un-packaged runs are better. It's a first step to expose failure modes — packaging is the right move once you've seen what un-packaged gets wrong.

The three-block memory frame the audit leans on travels as a frame for naming what you've already built, not a template to fill in. It makes an empty slot legible; it is not a checklist to author against.

This is the personal-layer habit that keeps a context system honest at scale. One person who audits and deliberately under-fills produces evidence-fed gaps instead of imagined ones — and that same discipline, test against a real run and fill from what it exposed, is what keeps a team's shared kit and a company's memory layer growing from real failures rather than from policy no one's work ever validated.
