Write the decision before you forget why

The principle: context as standing input — a decision that lives only in your head is invisible to every session that follows.

The instant a real architectural call resolves under pressure, write the four lines that capture it — context, decision, alternatives, and the one constraint that picked the winner — into a repo-resident record, while the why is still warm and free. layer: personal→team→company · phase: Context & Guardrails

The decision was real. The why evaporated — except the one line you wrote down.
The mechanism · two fates of the same decision

The choosing was cheap. Loading the context was the expensive part.

A threat-model pass flags one thing worth hardening. You weigh the trade-off, pick a side, ship the fix, and move on with the small relief of being past it. The relief is the trap. It feels like a decision banked — but the only thing you actually kept is the feeling of having decided, and a feeling is not an artefact. The reasoning that made one option obviously right was a whole loaded context: the attacker you were picturing, the alternative you rejected and why, the constraint that broke the tie. That context decays fast and silently. A week later someone in review asks "why this and not the obvious alternative?" and you find yourself reconstructing a rationale you no longer actually hold — or worse, defending a guess.

In an agentic workflow the decay costs twice. The agent that picks up adjacent work next week has no memory of the room where you decided. It reads the repo cold, sees a settled trade-off with no recorded reason, and does the rational thing: it re-litigates the call from scratch — sometimes landing on the option you already rejected, for the exact reason you already rejected it. Here's the counterintuitive bit. The expensive thing to preserve isn't what you decided — anyone can read the diff and see that you chose option X. The expensive thing is the constraint that made X obvious at the time. That single line is the test by which a future reader knows whether your call still holds when the inputs change. "We chose the stricter token scope because the endpoint is reachable unauthenticated" ages gracefully — the day the endpoint goes behind auth, anyone can see the call is now reversible. Strip the constraint and all that survives is a verdict with no expiry date, defended forever by reflex because nobody remembers what would falsify it.

A decision you can't reconstruct isn't a decision you still own — it's a guess you'll re-make under worse conditions.

The shelf-life upgrade · from private judgment to repo record

From the thought you'll keep to the file the agent reads cold.

The move is not "document more." It's a shelf-life upgrade on a single decision: take the rationale that currently lives as a fading thought — "I'll remember why" — and turn it into a numbered file the repo carries forward. The convention most teams reach for is an Architecture Decision Record: a short, standalone, repo-resident note, one per decision, numbered so they read as a history. Four labelled sections do the work — context · decision · alternatives · constraint — with the constraint section as the load-bearing one. Not a wiki page that rots in a corner, not a Slack thread that scrolls away, not a commit message buried in history. A file that the next session — yours or an agent's — cold-reads as part of the system's standing context.

Default convention

The path docs/adr/NNNN-slug.md and the four-section shape (context · decision · alternatives · constraint) are an illustrative default, not a mandate. Your repo's actual ADR path and section shape override it — if the team already has a convention, use theirs. The portable part is the discipline, not the directory name.

One ADR is a note. A repo of them is a different thing entirely — it's the layer the next decision rests on instead of fighting against. Each pass thickens the docs/adr/ directory, and each new constraint is read as standing context by whatever reads the repo next: a reviewer, a junior who wasn't in the room, a memory pass that loads prior decisions, or an agent doing adjacent work. The decision-recall doesn't depend on the person who made the call still being available — or still remembering. The loop below closes through the repo: decide, write the constraint warm, the directory accretes, the next session inherits the why, and decides the next thing on top of it rather than against it.

Use when

You just made a real architectural call under pressure — a STRIDE pass picked a threat to harden, a curated skill surfaced a trade-off and you committed — and the only record is the relief you're past it. Or you catch yourself saying "we decided that already" and can't point at where.

Build

A standalone, numbered, repo-resident record — docs/adr/NNNN-slug.md by default (your repo's convention wins) — with four sections: context, decision, alternatives, and the constraint that picked the winner.

Test

A teammate reads it and says "right, that's why."

Then it's a habit, not a chore: the why stops evaporating. Each constraint you bank is one the next reader — human or agent — never has to reconstruct.

Monday move: after your next real trade-off, stop for ninety seconds and write four lines into docs/adr/NNNN-slug.md (or wherever your repo keeps them) — context, call, the alternative you rejected, the constraint that decided it. An ADR is a markdown file in a directory you already own · no platform · no budget · no sign-off · ~90 sec. You're not proposing a process; you're writing down a decision you already made.

Why
The principle

Context as standing input. The ADR is the only channel by which a past judgment reaches a future agent.

"The expensive part of a decision was loading the context that made it obvious — and that context evaporates faster than the decision does."

The agent reading your repo has no memory of the room where you decided. A decision that lives only in your head is invisible to every session that follows — so the ADR isn't bureaucracy, it's the wire from a past judgment to a future reader. The constraint line is the highest-leverage sentence in the file: it's the test by which anyone later knows whether your call still holds when the inputs change. Strip it, and you've kept the verdict but lost the expiry date.

And the failure mode is specific. Treat the ADR as a checkbox after a menu-pick threat and you get paperwork — a fabricated trade-off written down to satisfy a form. The move is real only when the decision was real: name the worst thing the feature could do, find the threat adjacent to that answer, and record the constraint that resolved it. A genuine trade-off written down is design; a fabricated one is theatre.

A guess you'll re-make under worse conditions is not a decision you own.
Test · how you know it worked

The practitioner's "right, that's why" — the constraint line reconstructs the call without you in the room — beats a stranger's "well-formatted." Three more checks the file should survive: an agent picking up adjacent work builds on the constraint instead of re-deriving the settled trade-off; the four sections answer the hostile review question "why not the obvious alternative?" before it's asked; and the negative test — if the only record is that you feel past the decision, it didn't cross. Felt relief is not an artefact. Reconstructing the why a week later means the move never happened.
