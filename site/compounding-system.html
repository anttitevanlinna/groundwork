Build a compounding system

The principle: Persistence + automation = system. A chat cannot compound; a folder of markdown can.

Turn a standing challenge into a three-layer folder — raw sources, cite-backed memory, a narrow agent — so each session starts smarter than the one before, without you rebuilding context from scratch.

Same challenge. The chat forgets; the system remembers — and gets sharper.
The mechanism · why context disappears

The bottleneck isn't thinking. It's context that vanishes overnight.

Most CTOs have a standing challenge that never fully resolves — a platform migration, a talent gap, a market position question they keep returning to. Every week they re-open the same browser tabs, reconstruct the same context, re-read the same threads. The thinking isn't the bottleneck. The context is. And every chat window, by design, takes it with it when it closes.

The distinction that matters: if the next session starts from the same place the last one started, that's a chat. Useful in the moment, flat over time. A system is when the next session begins where today's ended — richer, sharper, already knowing what the previous pass established. That difference is not clever prompting. It's two ingredients: persistence and automation. Neither alone is enough.

"A chat cannot compound; a folder of markdown can."

The cite-back rule · what prevents smooth hallucination

Memory without cite-back compiles confidently and quietly invents.

The most insidious failure mode in any compounding system isn't obvious nonsense — it's a memory file that reads fluently, makes reasonable claims, and has no way to be checked. Agents smoothly hallucinate each other's memory. The cite-back rule closes that door: every claim in the memory layer carries the source file or URL it came from. When you push back on a claim, there's something to push back at. Without it, you're arguing with a confident mirror.

The rules layer has a different job: it keeps the system's shape consistent between sessions and between agents. Think of it as the standing brief — voice, what counts as a miss, patterns worth banning. It's short on purpose. A narrow rules file is load-bearing; a long one is noise the agent skims past. The PM agent's rules were narrow — a handful of lines. The narrowness was the feature. Build narrow, test with real work, sharpen as misses accumulate.

The compounding loop · where the system sharpens

Every miss is context you haven't written yet.

You spot mistakes by running the system and watching where it bends — not by reasoning about what the rules should say before you've seen the output. The compounding loop fires after a real run: the agent produces output, you find the miss, you write the rule, and the next pass starts with that miss closed. The durable artifact is never the morning output. It's the memory plus rules that made the next morning better.

The practical implication: treat the first build as a hypothesis, not a finished product. Three folders, one source, one memory file, one narrow agent — that's enough to start a loop. The system's value is not any single output. It's the memory that makes tomorrow's session start where today's ended. Boring on day one; dominant by day thirty — compound interest on a markdown folder.

What "Test" actually means · after a week

The memory is still worth reading after a week — and sharper than day one.

The test line for this pattern has a time component, and that's deliberate. A system that produces beautiful output on the first morning and degrades into noise by Friday isn't compounding — it's just a very good cold start. Run the system for a week, come back to the memory file, and ask whether you'd actually read it. If the answer is yes, and if you can trace every material claim to a source, the system is working. If the memory has grown fluffy, the cite-back rule wasn't enforced. If you wouldn't read it, the memory layer is summarising rather than maintaining.

The negative test is a general failure mode, not a war story: skip cite-back and a memory file quietly swells with unsourced "context" — and when you later ask the agent to trace a claim, it will confidently invent a source rather than admit it can't. A polished daily output hides it; the rot is in the layer underneath. The durable artifact wasn't the morning output. It was the memory plus rules that made the next morning better — and those had been neglected. Cite-back isn't bureaucracy. It's the mechanism by which the system stays honest under repetition.

Use when

The work should persist, sharpen, and run again without you rebuilding context every time. The challenge is live, stakes are real, and recurrence is guaranteed — it will come up again before Friday. If the next session starts from the same place the last one started, that's a chat, not a system.

Build

Three folders and a root rules file: sources/ · memory/ · agents/ · CLAUDE.md. A house-style file. A scheduled recurring output. The system, running.

Core moves

The action, in sequence

What changes = the system's ability to remember and sharpen.
1

Name the live challenge

One file — challenge.md. A specific, unsolved thing you're actually paid to move. Not "improve our platform." The thing that's been open for weeks.

2

Keep sources raw

Drop originals into sources/ untouched. Resist the urge to summarise pre-ingestion — that's the agent's job.

3

Compile memory with cite-back

The agent writes memory/ — every claim points to the source file or URL it came from. No citation, no claim.

4

Create one narrow agent

One markdown file in agents/. A handful of narrow rules beats a long file. Narrowness is the feature, not the shortcut.

5

Schedule the recurring output

Add fresh evidence, let the memory audit itself, schedule the output. A scheduled touch makes the difference between a build and a system.

Why
The principle

Persistence + automation = system. Neither alone is enough.

"A chat cannot compound; a folder of markdown can."

The bottleneck on your most important challenge is never more thinking. It's context that disappears overnight. A chat gives you the thinking but not the persistence. A folder gives you the persistence. Automation — a scheduled agent, a recurring output — is what turns a folder into a flywheel. Persistence without automation is just a well-organised archive. Automation without persistence is just a clever one-shot. Combined, each session starts where the last one ended.

The counterintuitive part: the architecture is embarrassingly simple. Three folders. Markdown. A rules file the agent reads cold. That simplicity is load-bearing, not a limitation. The moment you add a vector database, a pipeline, or a managed RAG layer before you've done a single compounding week with plain text, you've optimised the plumbing before you know what you're piping. Start with folders. Graduate to infrastructure when the plain-text system is worth protecting.

Where this sits: This is the personal foundation the entire personal OS rests on — without a compounding memory on your most important challenge, every other pattern in the language (judge loops, team sharing, system-building) is building on sand. Once it exists, it becomes the composable base that make-output-yours feeds voice into, that benchmark-the-judge runs quality checks against, and that the team promotes from personal to shared.
