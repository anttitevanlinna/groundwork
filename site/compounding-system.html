Agent memory

I feel the current limit of the LLM and code generating agents technology is the lack of memory suitable for working with complex and nuanced situations. The basic LLM remembers only so little in single chat. Once the context runs out, then the processing goes off rails. You can split your agents, then you need the memory of sorts even more. The human memory and thought-creation is excellent in making connections. LLMs are utterly unable to make connections outside of their current context window. A memory with similar properties as our thinking heads will likely be needed.

A chat is a conversation you have again; a system is a notebook that read itself before you sat down.

Keep your standing challenge the way a working scientist keeps a bench notebook — dated, append-only, every claim traceable back to where it came from. Concretely, that's a three-layer folder: raw sources, a cite-backed memory the agent maintains, and one narrow agent that cold-reads both — so each session starts smarter than the one before, not from scratch. What follows is a single page from one such notebook, eight days of it, reconstructed as a demonstration.

Where you start decides what you keep. The chat opens cold; the notebook opens where you left it.

Cover protocol · written before the first entry

Open the challenge you've been carrying for two weeks. Make three folders — sources/ · memory/ · agents/ — and nothing else. Drop in one source: a wiki page, a transcript, anything raw. Ask the agent to write a one-page memory from it, with a source beside every claim. That is the whole foundation. Everything below is one notebook obeying it.

Mon09:14

Opened a new notebook for the platform-migration question that's been on the whiteboard since March. Made the three folders, nothing else. Dropped in one raw thing — yesterday's architecture-review transcript, untouched, no tidying — and asked for a one-page memory/challenge.md with a source beside every claim. It wrote 847 words. Nothing I'd written about this challenge had ever survived a day. Tonight, for the first time, something will.

Tue08:40

Closed the lid yesterday, reopened it cold this morning — new session, empty context window. Before I'd typed a thing, the agent read memory/challenge.md and sources/ back to me: "Last session: competitor A's async gap, your integration strength — continuing from there." That sentence is the whole point. A chat would have asked me what we were working on. The notebook told me.

Wed11:02

Lost the morning to what looked like three separate bugs and was one. Our in-repo memory convention and the tool's own home-scoped auto-memory looked identical on disk; the agents kept conflating the two. That single confusion was the common cause behind all three breakages — earlier runs had just masked it with stale state. One agent stalled on the ambiguity and hung the full 1800-second turn cap before it died. Layer confusion doesn't announce itself; it wears a bug as a disguise.

Margin · rule written same day Keep the strata in named, non-overlapping homes. sources/ raw, memory/ agent-maintained, agents/ the rules — never one folder doing two jobs. Get the layers separate and the bugs that wore disguises stop appearing.
Thu07:55

Caught myself "helpfully" summarising the new vendor PDF before dropping it in sources/. Deleted my summary. Pre-digesting a source is the agent's job, not mine — and my tidy version would have buried the one line in the appendix that actually mattered. Sources go in raw; the agent compiles. The folder I'm least tempted to touch is the one that stays most useful.

Fri16:20

First real miss. The memory file stated a migration cutover date with no source behind it — read fluently, sounded right, was invented. This is the insidious failure: not nonsense, but a smooth claim with nothing to push back at. So I wrote the rule into the agents/ file, not into my own head: every claim carries the source file or URL it came from — no citation, no claim. Now when I doubt a line, there's something to check it against instead of a confident mirror.

Sat06:00

Ingested one fresh source overnight, refreshed memory/challenge.md, and flagged two claims whose sources had gone stale. The cite-back rule held: the flagged lines named exactly which source had moved. The notebook worked a Saturday I didn't. That scheduled touch is the line between a build and a system — automation is the thing a chat structurally cannot have.

“Context is KING / Context is learning” · Mar 2026 · unpublished

A chat cannot compound; a folder of markdown can.

Honest frontier · what one lap proves and doesn't
One eight-day page demonstrates the mechanism: the next session opened where the last ended, the memory got sharper, cite-back caught the one invented claim. What it does not prove is the trajectory — "boring on day one, dominant by day thirty" is the bet, not a measured result. A single lap can show you the curve has the right shape; only the thirtieth entry tells you how steep it really is. Log three more weeks before you claim the slope.
Why this, not a database
The architecture is embarrassingly plain — three folders, markdown, a rules file read cold — and that plainness is load-bearing, not a stopgap. Reach for a vector store or a managed retrieval layer before you've run a single compounding week and you've optimised the plumbing before you know what you're piping. Start with folders. Graduate to infrastructure the day the plain-text notebook is finally worth protecting.

My thinking is that text-based storage is the optimal way to store knowledge for the months to come. This is because ChatGPT and the competitors eat in text still much better than visual formats. I end up with a lot of files in folders.
