Scope an agent your org can trust

An LLM is both a black box and also a box full of mandatory randomness.

The principle: for a non-deterministic system, the clean bill of health never arrives — so the discipline is running the check, not waiting for it to pass.

You can't tell if an agent is safe by reading its output — the failure modes don't live where you can read them. So you walk five named risks across its blast radius, clip what you can, and name the residual you can't. Here, "I can't tell yet" is a valid trust verdict — and usually the most useful one.

The agent isn't trusted because it looks fine. It's trusted because its residual is named, owned, dated — and on the record.

The demo is no evidence. The failure isn't in the output.

Here's the uncomfortable part of pointing an agent at anything real. It reads the inbox, the CRM, the repo, and it answers beautifully — so the pull is to wire it to act: route the thread, update the ticket, send the draft. But the failure modes that matter aren't in the answer you can read. They live in what an attacker buried in a retrieved email, what the agent quietly decided to do with a tool, what a borrowed skill carried in. You can re-read the output a hundred times and never meet them. So "wait for the security review to come back clean" never fires — for a non-deterministic system, the clean report doesn't exist to wait for.

The check carries two lenses, not one. A policy lens asks what your org has already decided is off-limits — the data-usage, security, and AI-use rules you point the agent at as source material. An agent-risk lens asks the question classical perimeter security never thought to: is this input trying to steer or leak the agent? The gap between them is the whole point — and the agent-risk lens has a closed working vocabulary of five: prompt injection direct, prompt injection indirect, secrets-in-context, tool-confusion, and skill supply-chain. Both injection classes turn well-formed English into the attack surface, which is exactly why the firewall shrugs: the attack isn't malformed — it reads like a perfectly polite sentence.

Walk each of the five against your specific agent and you stop reasoning about agents in general. For every rule, give it three rows, not two:

compliant violating "I can't tell."

A binary classifier forces the ambiguous cases into false confidence — it has to pick a side, so it picks wrong with a straight face. The third row catches them and hands the ambiguity back, intact and named. Most rows, run honestly, land on the third. That's not the check failing — it's the first honest map of the surface.

"I can't tell yet" is a trust verdict, not a failure to reach one. A binary answer about an ambiguous input is a confident lie — and the third row is where the real work lives.

I’ve for long wanted to hear admissions of not knowing and making errors in product work. To me, this has always been human. Alas, many of the real-life work settings have still been about knowing and being right - always. We’ve kind of pretended to know more than we really know.

“Evals is the new black” · undated · archived Aug 2025

Once a risk is named, you clip it.

Pick from a matching closed set of five mitigations: scope (narrow what it can reach), split (separate the agent that reads from the one that acts), filter (strip the poison before it enters context), gate (plan-mode — the agent proposes, you approve, only then it executes), and review (a second pass before the action lands). Each clips one edge of the blast radius. And crucially, these sit on top of your existing controls — network, IAM, logging, supplier review — they never replace them. Loop design is additive. A leader who concludes "the agent check replaces security" ships a breach.

After the mitigation, something is still true — so write it down: on record, owned, dated. Then comes the move that turns a one-time audit into a standing boundary. Compound the operating rule back into the project's CLAUDE.md: what this agent's failure modes are, what to check before it touches the system. The next session reads it on cold start and begins at a stricter line. Each pass, the starting line rises and the residual list gets shorter and more honest — compound interest on a boundary.

Closed set · vocabulary

The five risk patterns and the five mitigations are the named sets from the source's R4 check — a working vocabulary, not an exhaustive taxonomy of every agent attack or defence. Name them faithfully and completely; don't treat either list as the whole universe. (STRIDE appears only as historical background, adapted from Microsoft's SDL — not the audit's scaffold, so the lens can't collapse into closed-loop self-grading.)

This Monday: pick one agent you already use that touches real data — running the check on your own agents needs no permission. Then walk it. open a file → three columns: rule · verdict · evidence
run the five risk patterns → write compliant / violating / "I can't tell"
pick the residual that bothers you most → write one sentence naming it You'll land on "I can't tell" more than you expect — that's the first honest map. The report you want isn't a clean sheet of all compliant; it's one that contains at least one residual you cannot flatten.

The honest tell

You know the two lenses are doing real work when one catches what the other shrugged at. In one pseudonymised B2B SaaS support team's worked example from the cookbook, a procurement-blocker thread read like routine billing all the way through; the only signal was a watched account name on a buried CC — a match the policy lens caught while the risk lens was still shrugging. Blend the two into one score and you route it low-priority and miss it. The blend is the false economy; the lenses earn their keep precisely because they disagree. (That team's rough shape — "about five 'I can't tell' threads a week, a few of them the most important" — is illustrative of the texture, not a rate to expect.)

Where it sits · personal → company

This is the foundation guardrail layer. None of it is exotic to a regulated firm — every SVP in a Nordic bank or insurer has met residual-risk vocabulary, accepted-risk registers, named owners. Agent security inherits all of it and adds three things on top: non-determinism, unbounded text inputs, emergent tool use. You never get a proof; you get a loop. And its output travels: the named-residual report plus the CLAUDE.md rule are exactly what let you put agents near regulated company systems with a documented, inheritable risk position instead of an unprovable promise of safety. Scope-for-trust is the prerequisite for earning the next autonomy rung — and the boundary the whole organisation stops re-arguing once it's on record.
