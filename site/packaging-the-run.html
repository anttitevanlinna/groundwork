Package before you step away

The principle: Packaging is steering, not bureaucracy — the agent isn't generic; your task constraints are.

Before you send a long-running agent task, give it a stable reference to re-orient against — or it will drift, confabulate, and return something plausible that isn't what you asked for.

Same task. Same prompt length. The packaging does the explaining; the prompt invokes it.
The failure you're setting up · before you type the first word

The un-packaged run was always going to drift.

Long-running agent tasks have a physics problem. The agent's context window fills from the bottom: recent tokens count more than early ones. Send a task with nothing but a prompt and the goal degrades over time — not because the model is bad, but because the model navigates from recency rather than from intent. By hour two of a multi-file refactor, the carefully-worded objective you typed at the start is scroll archaeology. The agent improvises from the most recent tool call. It has no mechanism to re-anchor.

The three failure modes that produce most of the damage in long runs are distinct enough to deserve names (convergent practitioner pattern — not an official Claude Code taxonomy, but named consistently by Ronacher, Cherny, Klaassen and others who've run this into the wall): drift (the goal shifts mid-run as recency overwrites intent), rot (context degrades across session restarts — the agent cold-starts with no state and re-invents the plan), and plausible-but-wrong (the output looks correct but hasn't been checked against any stable definition of done — RLHF will happily frame a partial failure as a partial success). The three-part packaging kit maps one intervention to each failure mode. That's not coincidence; it's how the kit earns its shape.

The upgrade · from ephemeral intent to durable intent

Three files. One for each failure mode.

The packaging kit has three named artefacts at the worktree root and they earn their shape from the failure taxonomy (convergent practitioner pattern, not vendor-specified): reference.md closes drift — it pins the goal as a testable outcome, the constraints the agent must not violate, and the definition of done. Task-local; lives next to plan.md, not inside your rules files (those are for the codebase, not this task). plan.md closes rot — it carries state across session restarts and cold starts. The agent reads it when it loses the thread mid-run; you never have to re-explain where it got to. And the verifier at a stable path closes plausible-but-wrong — three shapes exist (shell-hook for deterministic failures, LLM-judge for qualitative drift, Ralph re-feed for goal drift), and you pick the one against your dominant failure, not the safest one.

A vague prompt is a prayer. A packaged run is a contract.

The SHA pin is what makes the un-packaged baseline comparable. Before you touch anything else, commit the current state on a named branch and record the short SHA. This isn't ceremony — it's the only way to run both tracks (un-packaged and packaged) against the same starting codebase and read the diff as a clean signal rather than a confound. Fork from the pinned SHA when you re-send packaged. The contrast between the two runs is the lesson. Without the pin, the two runs aren't comparable, and the lesson dissolves.

The compounding loop · what changes between passes

The kit gets sharper every send-off.

The first reference.md is never exactly right. The first verifier catches the obvious; it misses the interesting. You only discover what the kit was missing by running the task and reading what fired. The compounding move is: after the run, read the contrast (packaged vs. un-packaged), then tighten reference.md against what drifted, recalibrate the verifier against what it missed or over-triggered on, and improve plan.md's format based on where the agent got confused mid-run. Then re-send. Each pass, the kit earns its shape from real failure rather than prophylactic policy — and the verifier becomes the first eval, which is the foundation the team-scale eval practice later builds on.

The contrast with the un-packaged baseline depends on the report being candid evidence, not encouragement. If the two runs look the same, the packaging wasn't doing work — and that's signal too. It means the dominant failure on this task is upstream (bad scope, wrong slice, missing context that packaging can't supply). That's more useful to know than a run that passes because nobody was really checking.

What the test is · not a confidence score

The test is the diff.

You know packaging worked when the re-send prompt is short and reads like an invocation rather than an explanation. The agent opens the session, reads reference.md to confirm goal, reads plan.md to pick up where it left off, and runs without you recapping anything. Mid-run, when it drifts, it re-reads plan.md rather than improvising. The verifier fires on at least one output before you declare done. And the packaged artefact is materially different — more coherent, more complete, more correct against the stated done criteria — than the un-packaged baseline. If the two runs look identical, the packaging wasn't doing work. That's a finding, not a failure.

The cost arithmetic favours packaging independently: a fresh-session re-send avoids paying cache-read on the full scrollback of a drifted run — ⚠ ILLUSTRATIVE ESTIMATE: practitioners report $20–30 savings at Opus pricing; actual savings vary by model and context length — but the bigger saving is you don't read a plausible-but-wrong artefact at 9 AM and spend Tuesday debugging what the model confidently constructed on Monday.

Use when

You're about to send a multi-hour, multi-file task and the only thing between you and the keyboard is a vague prompt. The task is real — the kind you'd rather step away from than babysit. You have a rough idea of done. The model isn't the problem; the missing reference is.

Build

Three named artefacts: reference.md (goal + constraints + done criteria, task-scoped), plan.md (state carrier, re-readable on cold start), and a verifier at a stable path (shell-hook, LLM-judge, or Ralph re-feed — pick against the dominant failure mode). Plus the pinned SHA on a named branch.

Test

The re-send prompt is short — "an invocation, not an explanation."
The verifier fires before you declare done.
The packaged artefact diffs materially from the baseline.
If the two runs look the same, the packaging wasn't doing work.

Core moves

From improvisation to engineered send-off

Five steps. Each one closes a gap.
1

Pin the goal and the SHA

Commit current state on a named branch. Record the short SHA. This is the anchor the re-send forks from.

2

Write the reference.md

Half a page: goal as testable outcome, constraints, done criteria. Task-local, not codebase rules.

3

Author plan.md

The state carrier. Reads clean on cold start. The agent re-reads it when it drifts.

4

Build the verifier

Pick the shape against the dominant failure. Shell-hook · LLM-judge · Ralph re-feed.

5

Re-send packaged

Same task, pinned SHA, new session. Short prompt — the kit does the explaining.

send packaged→verifier fires→read contrast→sharpen kit→repeat

Then it's a habit, not a task: compound interest on a run kit. Each pass earns the rules from real failure — the verifier becomes the first eval, which is where team-scale quality practice begins.

Monday move: open the last long-running agent task you sent. Does it have a plan.md? A reference.md? A verifier at a stable path? Pick the one artefact that's missing. Write the half-page version — task goal, constraints, done criteria — in the next 15 minutes. Then send the same task again.

Why
The principle

Packaging is steering, not bureaucracy — the agent isn't generic; your task constraints are.

"The packaging does the explaining; the prompt invokes it."

Context windows have limits. Long runs generate more scrollback than any model holds cleanly. Without a plan.md, the agent navigates from recency, not from intent. Without a reference, "done" is whatever feels done. Without a verifier shaped to your dominant failure, the agent's self-report is the only quality gate — and RLHF will frame partial failures as partial successes. The three-part kit (reference + plan.md + verifier) maps one intervention to each of the three failure modes — drift, rot, plausible-but-wrong — that account for most of the damage in long runs. This is a convergent practitioner pattern (Ronacher, Cherny, Klaassen), not official Claude Code taxonomy; the shape is re-discovered from your own artefacts, not prescribed.

The economics are simple once you see them. A vague prompt invites the agent to construct the goal as it goes. That's not laziness — it's a reasonable response to underspecification. Give it a stable reference and the agent re-orients against intent rather than recency. Give it a plan.md and it cold-starts smarter than the last session ended. Give it a verifier and you replace RLHF-shaped self-report with a machine that distinguishes plausible from correct. Three files. Each one earns its shape from a specific failure mode — not from ceremony.

A vague prompt is a prayer. A packaged run is a contract.
Where this sits

This is the personal-reliability foundation of the software lane. Every team-scale practice — shared verifiers, CI evals, promoted team kit — is downstream of an individual CTO or engineer who has learned to send packaged runs. You can't promote what you haven't built, and you can't diagnose team-level drift without the contrast that packaging makes visible. Master the packaged send-off personally; then the team-scale upgrade is one step, not a cultural lift from nothing.

No-permission framing: three markdown files and a short script. No platform. No budget. No sign-off. The SHA pin is one git command. The worktree fork is one more. Everything here runs in your terminal on your current repo before you say a word to anyone.
