Packaging a run

The principle: the prompt was never the thing you write — the packaging is, and the short prompt only invokes it.

You think the work of sending off a long agent task is wording the prompt. It isn't. The wording barely matters; what the agent finds on disk decides everything. Move the effort there and you can step away.

The thing you were optimising · was the wrong thing

The prompt is the least of it.

Here is the move most people get backwards. They labour over the prompt — phrasing the objective just so, stacking caveats, hoping a perfect paragraph will survive a four-hour run. It won't. A long agent task has a physics problem: the context window fills from the bottom, recent tokens outweigh early ones, and by hour two the careful objective you typed is scroll archaeology. The agent navigates from recency, not intent. No paragraph, however well-built, anchors against that.

So stop writing the prompt and start building the run. The agent re-orients against files on disk, not against the sentence that launched it — so that is where the steering lives.

Three failure modes do most of the damage on long runs, and practitioners who've hit the wall name them consistently (Ronacher, Cherny, Klaassen — a convergent pattern, not an official Claude Code taxonomy): drift, where the goal shifts as recency overwrites intent; rot, where the agent cold-starts after a session restart and re-invents the plan from nothing; and plausible-but-wrong, where the output reads correct because nothing checked it against a stable definition of done — and a model trained to be helpful will frame a partial failure as a partial success. You cannot out-phrase these. You package against them.

What does the work instead · one file per failure mode
reference.md
closes drift

Half a page: the goal as a testable outcome, the constraints the agent must not violate, the definition of done. Task-local — it lives beside the run, not in your codebase rules. The agent re-reads it to confirm goal.

plan.md
closes rot

The state carrier. It reads clean on a cold start, so the agent picks up where it left off across a session restart and you never re-explain where it got to. Mid-run, when it drifts, it re-reads this instead of improvising.

verifier · stable path
closes plausible-but-wrong

A check at a fixed path — shell-hook, LLM-judge, or Ralph re-feed. Pick the shape against your dominant failure, not the safest one. It fires pass-or-fail on the output, so self-report stops being the only gate.

One thing makes the lesson legible: pin the SHA before you touch anything. Commit current state on a named branch, record the short SHA, and fork the packaged re-send from it. Now the un-packaged run and the packaged run start from the same codebase, and the diff between them reads as clean signal rather than confound. That contrast is the whole point. If the two runs come out the same, packaging wasn't doing work — which tells you the real failure is upstream (bad scope, wrong slice, missing context no kit can supply). More useful to know that than to ship a run nobody was really checking.

And it compounds, because the first reference.md is never quite right and the first verifier catches the obvious while missing the interesting. You only learn what the kit was missing by reading what fired. After each run, tighten reference.md against what drifted, recalibrate the verifier against what it missed, improve plan.md's format where the agent got confused — then re-send. The kit earns its shape from real failure, not prophylactic policy, and that verifier quietly becomes your first eval — the foundation the team-scale eval practice is later built on. This is the personal-reliability floor of the software lane: you can't promote a packaged send-off the team hasn't seen you run, and the whole kit is three markdown files, a short script, and two git commands — all of it in your terminal before you say a word to anyone.

Right now: open the last long-running task you sent off and ask it the plain question — does it have a plan.md? a reference.md? a verifier at a stable path? Pick the one that's missing, write the half-page version in the next fifteen minutes — goal, constraints, done criteria — pin the SHA, and send the same task again. Read the two runs side by side.

You were never paid to write a better prompt. You were paid to build a run that finishes the job while you're somewhere else — and the prompt is just the doorbell.
