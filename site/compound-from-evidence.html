Grow rules from proof

The principle: Compound from evidence — rules grown from session signal outlast rules drafted from intent.

After each non-trivial session the agent reads its own transcript and rewrites the rules file in place. You push back, you commit. Boring on day one; dominant by day thirty.

Rules drafted from intent vs rules grown from proof. Only one survives the second session.
The mechanism · what actually happens

The session is evidence. Mine it.

Most engineers open a new session, do good work, ship the PR, and move on. The rules file — if one exists — stays exactly as written the week the repo was set up. It remains a generic wishlist: "be concise," "check your work." Indistinguishable from the default scaffolding that shipped with the template. The gap between that file and the one that knows your codebase is the cost you pay at the start of every session, forever.

The compound move closes that gap. On session close, run one prompt: "Review this session's transcript and diffs, rewrite the rules file in place, report what changed in 3–5 lines." The agent reads the actual signal — where it was pushed back, what it got wrong, what pattern produced a better result — and integrates that into the file. Not appended to the bottom. Integrated. Then you read three to five lines and push back on anything you cannot trace to a specific moment from today's session. If the rule couldn't have been written from this session, it doesn't belong here. Confabulation and evidence look identical until you check.

"Rules grow from evidence, not blank pages." The blank-page instinct produces policies. Evidence produces instruments.

The subtraction · what deletion means

Cut the rule the diagnosis killed.

Compounding is not pure accretion. After two runs of the same task, if a rule didn't fire, didn't help, or reflected a pattern you no longer use: delete it. Subtraction is compounding. The file is leaner, sharper, and the cold-start reads faster. The git history carries the evidence; a deletion commit that names the diagnosis is as valuable as an addition commit that names the session beat. A rules file whose history has no deletions hasn't been calibrated — it's been padded.

The upgrade · blank to calibrated

Three states of the same file. One shortcut.

Every rules file passes through three states. State zero: blank (or not created yet). State one: generic — written from best-guess intent on day zero. Looks reasonable. Says nothing specific. This is the dangerous state. A blank file knows it's empty; a generic file thinks it's done. The team onboards against it, the agent reads it cold every session, and nothing gets sharper.

State two: instrument — calibrated by evidence. This file has deletions in its history. Its rules name the moments that produced them. It reads short because the padding was cut. The shortcut to state two is not to write a better version on day zero. The shortcut is: start sparse, earn each rule. One compound step after the first real session and you're already past the generic state, because the evidence exists.

The compounding loop · what changes between cycles

Each cycle leaves the next one cheaper.

The compounding loop is concrete: you do the task, the session produces evidence, the compound prompt reads it, the rules file rewrites. The cold start next time opens with an already-calibrated instrument. The next session needs less course-correction to land. The cycle repeats. Each pass the rules node gets denser — and occasionally gets cut. Subtraction is visible in the loop too: a rule deleted is a calibration event, not a failure. The git history is the evidence log; each commit message names the session beat that produced the change. Not "update rules" — that's forecasting language. "add: validate webhook signatures before dispatch (payment-flow incident)" — that's instrument language.

At day thirty, the difference between a team that runs this loop and one that doesn't is legible in a single session. One opens with a file that already knows the codebase quirks, the failing patterns, the things that earn pushback. The other opens with whatever the template said. Both used the same agent. Only one made the agent cheaper per session.

What "Test" actually means · in practice

Read a rule aloud. Name the moment.

The test is concrete. Pick a rule in the file. Read it aloud. Can you name the specific session moment that produced it? Not the general problem it addresses — the moment. The exact pushback, the transcript line, the diff that forced the correction. If you can name it, the rule is evidence-backed. If you're reaching for a general principle, the rule was drafted from intent and the compounding hasn't started yet.

Use when

A non-trivial session just ended. The agent did something you didn't expect — good or bad. The PR shipped, the ticket closed, the session produced a surprise. The rules file still says what you typed two weeks ago.

Build

Why
The principle

Compound from evidence. Drafting rules before you have evidence is forecasting. Forecasters are confidently wrong; instruments are calibrated by use.

"Rules grow from evidence, not blank pages."

The reason a blank-page rules file underperforms is not laziness — it's the wrong epistemology. Forecasting produces confident generic statements. Evidence produces specifics. A `./CLAUDE.local.md` built from session evidence reads different from one drafted blank: concrete, specific, yours. The compound move treats the rules file as an instrument you calibrate by use — not a document you author once.

The compounding mechanism is exact: each unit of work makes the next cheaper — but only if the lesson gets encoded. The session without a compound step is like a sprint without a retro: it happened, nothing propagated. At the personal layer, the compounding surface is ./CLAUDE.local.md; the rate is set by how often you run the prompt and push back honestly. The personal organisational learning rate is the ceiling — this is the move that sets the floor.

The session without a compound step is a retro without a ticket. It happened. Nothing propagated.
Where this sits · personal → team → company

At personal scope this is the calibration engine — the move that turns sessions into a sharpening instrument. At team scope it becomes the quality gate: only rules that have evidence behind them earn a PR into the shared kit. Run it further and the same loop is what lets a team — then a company — compound rather than merely accumulate: the shared kit is only as calibrated as the personal files that earned their way in. Team-kit promotion builds on this pattern — compound-from-evidence is the prerequisite conversation before the team conversation starts.
