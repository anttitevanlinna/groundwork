Run N tasks in parallel

The principle: one session per working directory — isolate the tree, reconcile on the shared graph.

Give each parallel task its own working directory on its own branch, all sharing one Git history — so three agents can run at once without clobbering each other's files. The personal unlock that becomes a team's collision-free contribution model.

Three trees, one root. The model was never the bottleneck — the single working tree was.
The mechanism · why a branch isn't enough

Same two branches — the question is whether the tree moves under the session.

Once you trust the agent on one thing, the obvious move is to run it on three: a bug here, a refactor there, a small feature in a third corner. The hour you spent on one task could carry three. Then you point a second session at the same folder and they start clobbering each other. The reflex fix — git checkout a different branch — is worse than useless here: it overwrites the working tree in place. The editor and the running session are suddenly staring at file contents that changed under them; the session's scrollback now references files that no longer look the way it remembers, and the next turn goes sideways.

A clone fixes the collision the heavy way — a full second copy on disk, history severed — which is overkill for "I want two branches at once." Worktrees are the middle path: one repo, many working directories, each checked out to its own branch, all sharing the same underlying Git history. Switching between them is cd, not git checkout. Your original directory stays exactly where it was — zero checkout churn. Process diagram · 01A branch switch moves the tree under the running session; a worktree gives each branch its own directory, so cd replaces checkout and nobody loses their footing.

That's the whole reason the field reaches past branches and clones. Each option buys isolation; only one buys it without giving something up you needed to keep. Branches are cheap but pay at switch time — the session's footing. Clones are isolated but heavy — disk, plus a severed history that no longer reconciles. Worktrees give isolation without divergence: N working trees, one shared commit graph, so the sessions can't collide on disk yet every change still rides the same history and reconciles at merge. The bottleneck on running more agents was never the model. It was that one repo gave you one working directory.

Process diagram · 02Branches cost the session's footing; clones cost disk and a shared graph. Worktrees give isolation and shared history at once — and enforce the invariant for free.

The named principle reads like a tooling tip and is actually the thing the whole pattern protects: one session per working directory. Every collision failure mode — clobbered edits, stale scrollback, sideways turns — traces back to violating it. Two sessions in one folder and the later write wins; the earlier session's in-progress edit is gone from disk while its scrollback still believes the old content. Worktrees aren't the goal. They're the cheapest way to make the invariant hold while still running N sessions, which is precisely why Boris Cherny calls parallel worktrees the single biggest productivity unlock — a named practitioner's stance (Jan 2026 X thread + Pragmatic Engineer interview), not a measured or benchmarked finding.

The discipline keeps going past the start. Don't make one session narrate to the other what it did — that's asking two conversations to stay in sync by hand. Let Git carry the bits: commit, push a branch, or git stash push / cd / git stash pop. And when two worktrees touch the same file, the conflict surfaces cleanly at merge — Git stops both and shows the markers. This is the one place the human stays in the driver seat. Agents are confident and don't always read carefully enough at a merge boundary; you know what each change was for, Git knows the lines, you put them together. Do not let either agent auto-resolve.

The honest part: refuse to parallelise when serial is faster. Three cases earn a serial run. Ordering dependencies — a migration, then a backfill, then the reader code — where step three against pre-step-one state buys nothing and risks corruption. Greedy parallelism on small tasks, where the worktree coordination plus the conflict recovery loses to just doing the two tasks in sequence. And the case where you're still learning what "good" looks like in one session — a second session adds variables, not learning. The win is wall-clock time saved, not worktrees created. Test · how you know it worked

Three sessions run for an hour and none of them gets confused about what's on disk — each has its own scrollback, its own working directory, its own branch, and none references file contents that changed under it.

When two worktrees did touch the same file, the collision shows up as a clean merge conflict you resolve by hand — not as a silently overwritten edit you discover later. And the honest negative test: if you spent more time coordinating worktrees and recovering from conflicts than the tasks would have taken in sequence, the parallelism was the wrong call.

Then it scales: isolate the tree, reconcile on the shared graph, resolve by hand. The same discipline a whole team relies on when many contributors run many agents against one codebase.

Monday move: two unrelated tasks already in your backlog. A bug and a small refactor that don't depend on each other. git worktree add -b <task> ../<repo>-<task> · twice · one session in each. If they turn out to depend on each other, you learned the "when NOT to" lesson the cheap way. Worktrees ship with Git — the only thing you need permission for is your own restraint.

Why
The principle

One session per working directory. Isolate the tree; reconcile on the shared graph.

"One repo, many working directories — the model was never the bottleneck; the single working tree was."

Worktrees break the one-to-one between a repo and its working directory. The mechanism is isolation without divergence: N working trees, one shared history, so the sessions can't clobber each other on disk yet every change still rides the same commit graph and reconciles at merge. Branches gave cheap isolation but overwrote the tree under the running session; clones gave isolation but severed the history. Worktrees are the move that gives you both at once.

Which is why Boris Cherny calls parallel worktrees the single biggest productivity unlock — one named practitioner's stance (Jan 2026 X thread + Pragmatic Engineer interview), not a quantified or benchmarked result. Read the claim as a practitioner pointing at the lever, not as proof of a number. The lever itself is plain: the invariant the whole pattern protects is one session per working directory, and a worktree is the cheapest way to make it hold while still running N sessions.
